# Surfaces: one declaration, three ways in

Every feature Extend WP exposes to the outside is declared **once** as a
resource of the Motivar WP kit (`includes/kit/`, see its README) and
projected onto three surfaces:

| Surface | Generated by | Example |
|---|---|---|
| REST | `MammothWP\WpKit\Adapters\Rest_Adapter` | `GET /wp-json/extend-wp/v1/logs` |
| WP-CLI | `MammothWP\WpKit\Adapters\Cli_Adapter` | `wp ewp log list` |
| Abilities API | `MammothWP\WpKit\Adapters\Ability_Adapter` | `ewp-options/export` |

The declarations live in `includes/classes/ewp-surfaces/resources/` and are
registered by `EWP\Surfaces\EWP_Surfaces`. `Kit::on_ready()` only attaches
triggers; the registry itself (the resource classes, their services and the
three adapters) is built lazily by `EWP_Surfaces::boot()` on the first
`rest_api_init`, the first `wp_abilities_api_categories_init` /
`wp_abilities_api_init`, immediately under WP-CLI, or when something calls
`EWP_Surfaces::instance()->registry()`. A front-end or plain admin request
therefore never loads the resource layer (Setup.php also skips the
admin-only modules there — see `EWP\Request_Context`; `boot()` requires the
ones its resources wrap, `AWM_API` and `EWP_Options_Portability`, on demand).
The `ewp_surfaces_resources`
filter fires at that moment, not on `plugins_loaded`. Every trigger runs at
priority -1 so the adapters' own hooks (priority 10/20 on the same actions)
still fire within that action; inside `rest_api_init` the REST adapter is
attached with `add_action()` only, because `Rest_Adapter::register()` would
also register immediately and duplicate every route.
Each operation names the service method that runs it; the surfaces only
translate input and output. Parameters, authorization, validation and the
output schema therefore have exactly one definition.

Typed content resources expose abilities only: REST already serves every
content type under its own routes and the CLI through `wp ewp content
--type=`, so those surfaces are excluded with a recorded reason.
`MammothWP\WpKit\Inventory::export()` lists every operation with the routes,
commands and abilities it generates and the surfaces it deliberately skips.

Several resources are REST-only by declaration (`Resource::surfaces()`
returns `[Context::REST]`, or a callable that does while a feature is
enabled): the wp-admin field-builder/modal
helpers, the anonymous recently-seen recorder and the per-block editor
previews. They render for a browser script, so a command or ability would
have no caller, but they still get typed and described arguments, the
shared authorization path and inventory entries. The only routes that
remain hand-registered are the UI-configured dynamic API
(`AWM_Dynamic_API`, whose routes are data) and the `ewp-filter/{id}`
search results listed in `includes/classes/ewp-self-test/rest-only.json`;
a PHPUnit test fails when a route is registered that is neither generated,
covered by a self-test case, nor explained there.

## Authorization

Every operation declares one capability resolver, checked identically on
all surfaces by `Operation::run()`:

- Content operations use the content type's own `capability` for reads and
  writes. A type may opt into anonymous reads with `'public_read' => true`
  in its `awm_register_content_db` definition.
- Options and cache
  flushing `manage_options`; site info and the type inventory `read`; object search the
  `awm_object_search_capability` filter (default per object type since
  1.5.8: the post type's `edit_posts`, the taxonomy's `assign_terms`,
  otherwise `manage_options`; posts the user cannot read are left out).
- Anonymous callers get 401, authenticated callers without the capability
  403. An unattended WP-CLI run (no `--user`) is trusted as an
  administrator; with `--user` the capability is enforced like anywhere else.

`ewp_abilities_capability` still filters the capability of an ability, on
top of the kit's `mmwp_kit_operation_capability`.

## Destructive operations

Deletes, log cleanup and content import are declared destructive. On the
Abilities API they require `confirm: true`; on the command line `--yes`;
REST relies on the HTTP verb. The options import is a dry run by default
for abilities (`dry_run: false` plus `confirm: true` writes), and runs for
real by default over REST and the CLI as before.

## Per-surface behaviour that is deliberate

Surface differences are declared in the resource, never in three classes:

- **Options export**: REST still accepts the admin form's `pages` and
  `option_pages[]` names; the CLI defaults to every page and writes
  `--file`.
- **Content export**: REST answers with the payload encoded as a string
  (the admin screen downloads it); import answers `true`.
- **Object search**: REST keeps `{success, data}`; abilities get
  `{count, results}`.

## Adding a feature

1. Put the logic in a service class with plain PHP inputs and outputs.
2. Declare a `Resource` (or add an operation to one) under
   `includes/classes/ewp-surfaces/resources/` describing its fields,
   capability, output schema and surface bindings. Descriptions are
   mandatory: they become the REST arg descriptions, `wp help` and the
   ability schema.
3. Register it in `EWP_Surfaces::boot()` or through the
   `ewp_surfaces_resources` filter.
4. Add a self-test case (or extend one) and list the new routes, commands
   and abilities under its `covers` in `manifest.json`.
5. Run both test suites. `tests/test-surface-parity-test.php` fails if any
   declared surface is missing or undocumented; the manifest test fails if
   any generated surface is uncovered.

Never register a route, command or ability by hand for a feature that has
a service; declare it.

### Leaving a layer out

Every operation lands on REST, CLI and abilities unless told otherwise. When
a whole resource has no use for one layer, override `Resource::surfaces()`
(and `surfaces_reason()`) once instead of repeating `->surfaces()` on each
operation — `Content_Resource` (no REST, served per type) and the typed
content resources (abilities only) do this. A single operation can still
call `Operation::surfaces()` to differ from its resource. The reason is
recorded in the inventory so the parity test can tell a deliberate omission
from a missing registration.
